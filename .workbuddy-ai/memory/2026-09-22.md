# 2026-09-22

## Android CI 链接失败：开 HXCPP_STACK_TRACE 撞上 hxcpp 的对象缓存

### 现象

CI（macOS runner 编 Android aarch64）在链接 `libApplicationMain-64.so` 时报一片
undefined symbol，两类：

```
undefined symbol: hx::ExceptionStackFrame::ExceptionStackFrame(hx::StackFrame const&)
    referenced by DefineMacro.cpp / DefinesMacro.cpp / Iris.cpp ... referenced 577 more times
undefined symbol: _hx_pos_a12cec1f7f1a6feb_18_new
    referenced by Iris.cpp: crowplexus::iris::IrisCall_obj::__alloc(...)
undefined symbol: _hx_pos_62c77a219906a331_7_new   (haxe::ui::CallLater_obj::__alloc)
undefined symbol: _hx_pos_74e540f925efc24d_3_new   (haxe::ui::filters::Blur_obj::__alloc)
... 每个都是某个类的 new
```

编译命令行里能看到宏确实生效了：
`-DHXCPP_CHECK_POINTER(haxe) -DHXCPP_STACK_TRACE(haxe) -DHXCPP_STACK_LINE(haxe)`。
但整份日志只有 `Compiling group: haxe (16 files)` —— **只重编了 16 个文件**。

### 根因：hxcpp 的对象名不含编译参数

`_hx_pos_<hash>_<line>_<name>` 的声明与定义是**分开**的：

- `include/<...>/IrisCall.h:9` → `HX_DECLARE_STACK_FRAME(_hx_pos_..._18_new)` = `extern ::hx::StackPosition ...;`
- `src/<...>/IrisCall.cpp:8` → `HX_DEFINE_STACK_FRAME(_hx_pos_..._18_new, ...)` = 真正的定义

而 `HX_DEFINE_STACK_FRAME` 在 `HXCPP_STACK_TRACE` 未定义时**展开成空**
（`include/hx/StackContext.h:81-92`）。CI 上 `Iris.cpp` 被重编（引用出现了），
`IrisCall.cpp` **没被重编**（定义还是"空"）→ 链接期符号对不上。

为什么没被重编 —— hxcpp 的两种对象命名（`tools/hxcpp/Compiler.hx`）：

| 函数 | 名字构成 | 参数相关？ |
|---|---|---|
| `getObjName(inFile)` | `Md5(targetKey + path.dir + group.mId).substr(0,8) + "_" + name` | **否**，只跟目标/路径/组有关 |
| `getHashedName(inFile, getArgs(inFile))` | `Md5(源文件内容 + 编译参数 + 依赖哈希 + 编译器版本)` | 是 |

`getCachedObjName()` 只在 `mCompilerVersion!=null && useCacheInPlace && group.isCached()`
时走 `getHashedName`，否则走 `getObjName`。CI 上的对象名是
`c2568664_DefineMacro.obj` / `57d14e5a_Iris.obj` —— **`getObjName` 形式**，
所以改 `-D` 不会让它们失效，只有 `.cpp` 内容变了的 16 个被重编。

→ **改这类全局宏必须先把 `obj/` 清掉**，否则新旧对象混链。

`hx::ExceptionStackFrame::ExceptionStackFrame` 缺失是同一件事的另一面：它定义在
`src/hx/Debug.cpp:441`（也在 `#ifdef HXCPP_STACK_TRACE` 里），属于 hxcpp 自己的库，
同样因为没重编而缺符号。

### 本次改动

`Project.xml` 的 `<section if="cpp">`：两个新宏加 **`unless="android"`**。

```xml
<haxedef name="HXCPP_STACK_LINE" unless="android" />
<haxedef name="HXCPP_STACK_TRACE" unless="android" />
```

理由：
- Android 的 `-D` 集合回到上次绿色构建的**完全相同**状态 → CI 不需要清缓存就能绿。
- Android 本来就走 `NativeCrashHandler` + 自己的 crash logger，Haxe 侧栈读不回来，
  却要付每次函数进出的 `pushFrame`/`popFrame` 代价。
- 和已有的 `HXCPP_CATCH_SEGV if="debug" unless="android"` 一个路数。

### 遗留：Windows 那棵树必须清一次对象

本地 `export/legacy-gc/windows/obj/obj/msvc1964-nc/` 有 **5389 个 .obj**，
全是没开宏时编的。下次 Windows 构建会原样复用 → **同样的 undefined symbol**。
要清的是 `export/legacy-gc/windows/obj/obj/`（不是整个 `obj/`：生成的 .cpp 内容
不随这两个宏变化，只有 C++ 预处理结果变，所以重新编 C++ 就够；但重建整个 `obj/`
更保险）。代价是一次全量重编（上次约 2 小时）。

注意：这批对象现在是一致的（都没开宏）。所以**如果决定不要栈，什么都不用做**；
一旦用新宏构建过一次，两个方向都得清一次对象。

### 待确认

改动没有编译验证（`lime` 在这个 shell 里跑不了，见下）。Android CI 是否真的绿了、
Windows 清对象后是否正常出栈，都要等实机。

### 环境备注

`lime update` / `lime build` 在我的 shell 里报 `Could not find haxelib "modcharts"`
（`haxelib path modcharts` 正常，`haxelib config` 也指向项目内仓库）—— 沙箱环境问题，
与项目无关。所以**没法自己重新生成 hxml 或验证 Project.xml 的宏落地**。

## Android 16 KB 页对齐：hxcpp 链接用了 runner 自带的 NDK r27d

### 现象

release APK 在 16 KB 页大小的设备上启动即弹 SDL 错误：

```
dlopen failed: ".../lib/arm64/libApplicationMain.so"
  program alignment (4096) cannot be smaller than system page size (16384)
```

### 取证（可直接复用）

从 APK 里抽出四个 arm64 `.so`，逐个看 ELF LOAD 段对齐（`llvm-readelf -l`）和
`.note.android.ident`（记录**编译它的 NDK 版本**）：

| .so | 构建者 | LOAD 对齐 | ident 里的 NDK |
|---|---|---|---|
| `libApplicationMain.so` | **本仓 hxcpp 链接**（唯一自己编的） | **0x1000** ❌ | **r27d** |
| `liblime.so` | lime haxelib 自带的预编译 `ndll/Android/liblime-64.so` | 0x4000 ✅ | r29 |
| `libc++_shared.so` | NDK 自带 | 0x4000 ✅ | — |
| `libvlc.so` | hxvlc 随包发的预编译产物 | 0x4000 ✅ | — |

后三个都不是 CI 编的，ident 只反映打包 haxelib 的人，**别拿它们推本仓的 NDK 版本**。

`.note.android.ident` 前 4 字节是 API level（这里 0x15 = 21），紧跟 ASCII 版本号。
**以后判断某个 .so 是谁、用什么 NDK 编的，读这个 note 最快。**

实测（`clang++ -shared --target=aarch64-linux-android<API>`）：NDK r28c 下 API 21~35
**全部**输出 `0x4000`；只有显式 `-Wl,-z,max-page-size=4096` 才得到 `0x1000`。
即 4096 只可能来自 r27 及以下的默认值。

### 根因（用兄弟项目 Frozen Engine Mobile 对照确认）

同门项目 `D:\FNF-FrozenEngine-Moblie` 配置同样写着 r28c，**实测能跑**。抽它的 APK
验证：`libApplicationMain.so` 的 ident 是 **r28c**、LOAD 对齐 **0x4000** ✅。
两边唯一有意义的差异就是 workflow 里 `lime config ANDROID_NDK_ROOT` 写的是什么：

| | `lime config ANDROID_NDK_ROOT` 的值 | hxcpp 实际用的 | LOAD 对齐 |
|---|---|---|---|
| 移动版（能跑） | `${{ steps.setup-ndk.outputs.ndk-path }}` = r28c | r28c | 0x4000 ✅ |
| NovaFlare（崩） | `$ANDROID_NDK_HOME` = 镜像预置 r27d | r27d | 0x1000 ❌ |

链条三跳，缺一不可：

1. `lime config ANDROID_NDK_ROOT <path>` 把值写进 lime 的 config。
2. `lime build` 把 config 值放进 `project.environment`，再**逐个回灌进进程环境**：
   `lime/git/src/lime/tools/HXProject.hx:499-502`
   —— `for (key in project.environment.keys()) Sys.putEnv(key, ...)`。
3. hxcpp 把整个进程环境灌进 defines（`hxcpp/git/tools/hxcpp/BuildTool.hx:1522`
   —— `for (e in env.keys()) defines.set(e, Sys.getEnv(e))`），而
   `Setup.hx:417` 见 `ANDROID_NDK_ROOT` 已存在就**直接用、不再探测**。

→ 结论：**workflow 里 `lime config ANDROID_NDK_ROOT` 写什么，hxcpp 就用什么链接。**

⚠️ GitHub `macos-14` / `macos-15` 镜像都预装三个 NDK，且**默认是 r27d**：
`ANDROID_NDK` / `ANDROID_NDK_ROOT` / `ANDROID_NDK_HOME` = `.../ndk/27.3.13750724`；
另有 `28.2.13676358`（**就是 r28c**）、`29.0.14206865`（`ANDROID_NDK_LATEST_HOME`）。
`setup-ndk` 要 r28c 时直接复用镜像里已装的 `28.2.13676358`。

r28 起才默认 16 KB 对齐；r27 及以下要手动加
`-Wl,-z,max-page-size=16384 -Wl,-z,common-page-size=16384`。

### 本次改动

`.github/workflows/MobileBuild.yml`（Android job）四处：

1. `Setup Android NDK` 加 `add-to-path: false`（不让 action 往 PATH 塞工具链）。
2. **`Configure Android` 的 `lime config ANDROID_NDK_ROOT` 从 `$ANDROID_NDK_HOME`
   改成 `${{ steps.setup-ndk.outputs.ndk-path }}`** —— 这是真正的修复点。
3. 新增 `Export Android NDK`，把 ndk-path 写进 `$GITHUB_ENV`（兜底，防 lime 改回灌行为）。
4. 新增 `Export` 之后的 `Force 16 KB linker flags for hxcpp`：写 `$HOME/.hxcpp_config.xml`
   给 android 的 dll linker 加两个 page-size flag（补 `common-page-size`，
   因为 r28 的默认只给了 `max-page-size`）。
5. 新增 `Verify 16 KB page alignment` 门禁（`Compile Android` 之后、打包之前）：
   **LOAD 对齐 < 16384 就 `::error::` 失败；RELRO 只 `::warning::`**。

第 5 步已用两套**真实产物**跑过（把 workflow 里的脚本原样抽出来执行）：
移动版那套退出码 0、只有 RELRO 告警；NovaFlare 那套退出码 1，精确报出
`libApplicationMain.so 的 LOAD 段对齐 0x1000`。YAML 用 pyyaml 解析通过、步骤顺序正确。

RELRO 只告警的理由：官方要求 `(VirtAddr + MemSiz) % 0x4000 == 0`，但**能正常启动的**
移动版产物余数是 12288（非 0）—— 这条在实机上并不总是致命，不该拿它卡发布。

**未做**：`android.yml`（`oldbuildtest`，`workflow_dispatch`）仍是 **NDK r21e** +
同样的 step 级 `env:` 写法，一样会产出 4 KB 的 .so。它不只是环境变量的问题——
r21e 整个工具链都早于 16 KB 支持，要修得先换 r28+。

### 已知不需要动的

`Project.xml` 没设 `android.target-sdk-version`，走 lime 默认 **targetSdk 36 / minSdk 21**
（release APK 里实测 `targetSdkVersion:'36'`、`compileSdkVersion='36'`）。

⚠️ lime 的 `templates/android/template/gradle.properties:23` 把
`ANDROID_BUILD_SDK_VERSION` **直接赋成** `ANDROID_TARGET_SDK_VERSION` —— 改 targetSdk
会连 compileSdk 一起变。所以"把 targetSdk 降到 30"在这个项目里等于把 compileSdk 也降到 30，
AGP 8.6 + AndroidX 依赖会直接编不过。

**targetSdk 与 16 KB 无关**：对齐检查发生在动态链接器按 ELF `p_align` 映射 PT_LOAD 段时，
是加载器层面的硬校验，不受 manifest 里任何字段影响。降 targetSdk 不解决这个崩溃。

## 21:00 之后：Android 模拟器启动崩溃取证（a16bf467）

铁镐报"NF 在安卓虚拟机里起不来，报告没给有效消息"。用 adb 连上 AVD 实测了一轮。

- **设备**：`emulator-5554` = `sdk_gphone16k_x86_64`（Android 17 / API 37 / x86_64 /
  `PAGE_SIZE=16384`）。adb 在 `C:\Users\Ice_Axe\AppData\Local\Android\Sdk\platform-tools\`，
  **不在 PATH**。包 `com.NovaFlareEngineNew`，`primaryCpuAbi=arm64-v8a`（走 ndk_translation）。
- **报告为什么空**：`Project.xml:311-312` 的 `HXCPP_STACK_LINE` / `HXCPP_STACK_TRACE`
  带 `unless="android"` → Android 上生不出栈。`[native_hxcpp_exception_stack]` 是 `[]` 即指纹。
  `Project.xml:309-310` 注释里"Android 走 NativeCrashHandler，读不回 Haxe 栈"的理由
  **实测不成立** —— 本次就是 Haxe 路径报的（`kind=uncaught_error`），进程也没死。
- **日志通道**：logcat tag **`trace`**（`Sys.println` 被 lime 重定向），
  以及 `/sdcard/.NovaFlare-Engine/crash/`（cwd 由 `Main.hx:323 Sys.setCwd` 设定）。
  `/sdcard/Android/data/<pkg>/files/` 不存在。
- **崩点**：`nativeRunMain` → OpenAL 初始化成功 → 2 秒后 `Null Object Reference`。
  `used_bytes=6655088`（≈6.6 MB，启动早期），与铁镐那份完全一致 → 确定性复现。
  屏幕纯黑 + 原生弹窗抢焦点；进程未死。
- **16 KB 对齐已修好**：设备上 `libApplicationMain.so` 四个 `PT_LOAD` 全 `p_align=0x4000`，
  GNU_RELRO 余数 0，NDK r28c。所以本次启动失败不是对齐问题。
- **Windows 侧** `crash/2026-09-22-10'56'30.txt` 是**另一个** bug
  （`PsychCreditsSubState.create() line 97`，堆 186 MB），与本次无关。
- **结论/下一步**：给了三条路 —— 撒面包屑（`trace` 进 logcat，最省）、给 Android 开栈宏
  （须先删 `obj/`，且 Project.xml 无 `&&` 先例）、试 Windows 复现。
