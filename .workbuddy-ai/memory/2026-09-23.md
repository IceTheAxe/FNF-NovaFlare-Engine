# 2026-09-23

## CI 缓存从"固定 key + 整 export 目录"换成内容寻址

原来是上游带来的写法：固定 key（`cache-build-Android` / `cache-build-iOS` / `cache-build-haxelib`）
+ 缓存 `export/legacy-gc/<平台>/`。两个问题：固定 key 存不进第二遍（只有 `InstallHaxelib.yml`
记得先删旧条目再存，MobileBuild 那两处没有）→ 缓存永远冻在第一份；缓存 `export/` 靠 mtime 复用，
CI 上必然失效（源文件 mtime 每次都是"刚刚"）。

### 改了什么

- `MobileBuild.yml`：Android / iOS 两个 job 各加 job 级 `env: HXCPP_COMPILE_CACHE`，
  Compile 命令行加 `-D`，新增 `Restore/Save hxcpp cache`
  （滚动 key `nf-hxcpp-<os>-<arch>-<android|ios>-<run_id>`，path `.hxcpp_cache`，
  save 用 `if: always()` + `continue-on-error`）。
- 依赖缓存：path `.haxelib/` → `~/haxelib`（Install 那步是 `haxelib setup ~/haxelib`，
  库根本不在工作区那个目录里），并去掉 `export/legacy-gc/<平台>/`；
  key 从固定值换成 `nf-deps-<os>-<android|ios>-<hashFiles('hmm.json')>` ——
  内容 key：依赖没变就精确命中、也不会重复上传，变了自然换 key。
- `InstallHaxelib.yml`：缓存 path `.haxelib/` → `~/haxelib`。
- 新增 `hxcpp-cache.yml`（workflow_dispatch，list / prune）：滚动 key 必须有人收敛，
  否则会把 10 GB 配额吃光。`CACHE_PREFIX: nf-` 同时覆盖两族 key，分组规则按族分开
  （滚动 key 去 run_id，依赖 key 去末尾那段 hash）。
- iOS job 里 `git -C .haxelib/lime/git` 两条诊断改成 `~/haxelib/...` —— 写错时只打印 git 的报错，
  步骤照样绿（最后一条命令是 echo），这两个诊断一直是空的。

### 为什么这里能用内容寻址（读过源码）

hxcpp 只把 `toolchain/common-defines.xml` 白名单里的宏（`HXCPP_*`）转成 C++ `-D`
（`Compiler.getCompilerDefines()` 读的是 build.xml 的 `<flag>`，没有"所有 define 都塞进命令行"那条路），
所以 `-Dcommit_sha` / `-Dbuild_number` 这种每次构建都变的 define **不会打散对象 hash** ——
只有真读它的 `MainMenuState.hx` 那几个 .cpp 会重编。这是能不能上内容寻址的前提。
`CompileCache.init()` 会自己 mkdir 缓存目录，不用预先建。

### 验证

pyyaml 解析三个改动文件通过；两个 job 的 restore/save key 逐字相同、Compile 带 `-D`、
步骤顺序正确（restore 在 Install / Compile 之前，Save hxcpp 紧跟 Compile）；
prune 的分组函数对两族 key 各试一条，分组正确。

### 未动（看到了但没碰）

- `MacBuild.yml`：`Determine cache strategy` 两个分支都 `use_cache=false` → 那个 restore 是死代码；
  它的 `.haxelib/` 路径同样对不上。
- `android.yml`（oldbuildtest）：NDK r21e，缓存 `~/haxelib` + `export/.../{haxe,obj}`，同样靠 mtime。

### 两个额外发现

- **`InstallHaxelib.yml` 没有任何调用方**：`release.yml` 只调 MobileBuild / MacBuild /
  WindowsBuild / LinuxBuild，全仓没有 `uses: ./.github/workflows/InstallHaxelib.yml`。
  它只能手动 dispatch；它写的 `cache-build-haxelib` 也没人读（唯一读它的 MacBuild 那段 restore 是死代码）。
- **两处 `zip -r /Users/runner/haxelib.zip .haxelib/`**：CI 上 `.haxelib/` 是空的（库在 `~/haxelib`），
  而 `zip` 遇到不存在的目录会以 12 退出、把 job 搞红 —— 这个产物一直是空壳。
  MobileBuild 那处加了 `mkdir -p .haxelib` 兜底（它原来可能靠缓存 restore 顺手建出这个目录，
  我把 `.haxelib/` 从缓存路径里去掉后就没这回事了，等于把风险还原成零）；InstallHaxelib 那处没动。
  真要一份能用的依赖包，该 zip 的是 `~/haxelib`，但那有几百 MB，不该塞进每次构建。

## 去掉 MobileBuild.yml 里的 -D HXCPP_COMPILE_CACHE

早先按"env + -D 双通道"写的，实测证明 `-D` 那条在 Windows 上会被上游把值拼坏：hxcpp 收到
`<路径>=<路径>`（反斜杠还翻了一倍），`CompileCache.init()` 拿它建目录失败、缓存静默失效。
FE 两仓的 `Main + Release #64` 就是这么红的。NF 这两个 job 跑在 macOS、路径里没有反斜杠，
所以没炸 —— 但没理由留一颗雷。

改动：Android 的 if / else 两条 Compile 命令、iOS 那条 Compile，都删掉
` -D HXCPP_COMPILE_CACHE=$HXCPP_COMPILE_CACHE`（job 级 `env` 保留，够用 ——
`BuildTool.runMain()` 开头就把 `Sys.environment()` 灌进 defines）；
`hxcpp-cache.yml` 里"env 和 -D 都设了，两条路都通"改成"只走环境变量"。

## 把 FE 的 Win8 风格 GameplayChanger 移植到 NF

`substates/GameplayChangersSubstate` 从"`Alphabet` + `CheckboxThingie` 列表"换成
Win8 风格侧边面板（从 FE 的 `options/Win8CharmSettings` 那一套搬过来）。

### 落点：新建独立顶层包 `source/win8/`

**没有碰 `source/options/**`、`MouseMove`、`ClientPrefs`、`Language`、`import.hx`。**
原因是 NF 的 `options/objects/backend/{BoolButton,NumButton,StringSelect}` 已存在（不同实现），
照搬 FE 路径会覆盖 NF 自己的设置界面；而 NF 的 `Option extends FlxSpriteGroup` 又强耦合
`OptionCata` / `OptionsState`，喂不进这套控件。所以自带一份纯数据的 `win8.PanelOption`，
新建 `win8` 包避让 —— 同一顶层包内类型自动可见、无需 import，NF 的全局 `import.hx` 零改动。

14 个新文件：`Panel`(基类) / `PanelOption` / `WidgetFactory` / `OptionType` / `Input` /
`Theme` / `Icons` / `BoolButton` / `NumButton` / `StringSelect` / `OptionButton` /
`OptionRow` / `OptionSection` / `PanelIconButton`。

### 与 FE 的差异（都是刻意的）

| 项 | FE | NF |
|---|---|---|
| 配色 | `UITheme` 深浅色 + `UIControlTheme` 主题 | 固定 Win8 深色，强调色取 `EngineSet.mainColor` |
| 控件↔面板耦合 | 控件直接读 `OptionsState` / `OptionsPageState` | `WidgetFactory` 上三个静态标记（`popupOpen` / `scrollVelocity` / `suspendScroll`） |
| 语言 | `Language.getPhrase` + 热重载 | NF 的 `Language` 只有 `get()`，直接用英文串 |
| 选项数 | 9（多 `opponentplay` / `mirrornotes`） | 保持 NF 原有 8 项 |
| 虚拟按键 | 无 | 无（且 hxml 里有 `NO_FEATURE_TOUCH_CONTROLS`，旧实现的 `addVirtualPad` 本来就没编进去） |
| 滚动 | `scroller.useViewSpace` / `dragSensitivity` / `deceleration` | NF 的 `MouseMove` 没有 / 是 private，删掉这三行 |

### 落盘时机

沿用旧行为：`closePanel()` 里统一 `ClientPrefs.saveSettings()`，不做即时落盘
（NF 的 `saveSettings()` 要重写主存档 + 按键存档 + 箭头颜色文件，成本不低）。

### 验证

两棵树都跑过类型检查 + hxcpp 代码生成，均 exit 0：
`export/release/windows/haxe/release.hxml`（`hxcpp_zgc`）与
`export/legacy-gc/windows/haxe/release.hxml`（`legacy_gc_compare`）。
产物抽查：`obj/src/win8/` 14 个 .cpp 全在，`Panel.cpp` 里 `MouseMove_obj::__alloc(...)`
的参数与预期一致。

**只验证到"能编出来"，没有实机跑过。** 下面几处需要铁镐进游戏看一眼：
滑块填充条的渲染（`_frame.frame.width` 裁源帧那套）、面板滑入滑出的手感、
下拉弹层在贴右面板边缘时的夹取位置。
