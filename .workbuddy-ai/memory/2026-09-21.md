# 2026-09-21

## 报错处理流程改造：让 Haxe 层优先接住错误

### 诊断出的机制

NovaFlare 有两条互不相通的报错路径，同一个错误走哪条取决于一个编译宏：

- **Haxe 路径**：`Stage.__broadcastEvent` 的 try/catch → `__handleError` → `UncaughtErrorEvent`
  → `mobile.backend.CrashHandler.onUncaughtError` → 写 `crash/<时间戳>.txt`，`preventDefault()`
  让游戏继续跑。
- **原生路径**：`general.backend.NativeCrashHandler` 的 `AddVectoredExceptionHandler` +
  `SetUnhandledExceptionFilter` → 写 `native-crash-*.txt/.dmp`，`EXCEPTION_EXECUTE_HANDLER` 杀进程。

`HXCPP_CHECK_POINTER` 是分水岭：开了，`obj.field` / `arr[i]` 的空引用会走
`hx::NullReference` → `hx::Throw` → 真 Haxe 异常，被帧循环的 catch 接住；不开就是裸
`EXCEPTION_ACCESS_VIOLATION`，完全绕过 Haxe 层。

它随 `HXCPP_DEBUG` 自动开启（`.haxelib/hxcpp/git/include/hxcpp.h:109`），而 Release 没有
`HXCPP_DEBUG`，所以必须显式写进 `Project.xml` 才在 Release 生效。
转发链路：`Project.xml` haxedef → 生成的 hxml `-D` → hxcpp
`.haxelib/hxcpp/git/toolchain/common-defines.xml:12` 的 `<flag value="-DHXCPP_CHECK_POINTER" if="HXCPP_CHECK_POINTER" tag="haxe" />`。

缺口范围：`obj.field` / `obj.method()` / `arr[i]` / `arr.length` / `cpp.VirtualArray` /
`Scriptable` 受控；`null + 1`、`nullFn()` 本来就无条件抛 Haxe 异常，不受宏影响。

`Stage.__broadcastEvent` 的 `catch` 块里调 `__handleError(e)`，**不在 try 内** —— 所以
`onUncaughtError` 自己抛异常会逃出整条 Haxe 链路，变成原生崩溃（`0xe06d7363`）。

### 本次改动

- `Project.xml`：恢复无条件 `<haxedef name="HXCPP_CHECK_POINTER" />`；把
  `openfl-disable-handle-error` 笔误改成 `openfl_disable_handle_error`。
- `source/mobile/backend/CrashHandler.hx`：抽出 `writeHaxeCrashReport(kind, message, stackLabel,
  stack, callStack)`（永不抛，带同消息 2s 去重）；`onUncaughtError` 拆成外层 no-throw 壳 +
  `reportUncaughtError`，修掉 stack 遍历里 `file` 可能为 null 的 `NullReference`；
  新增 `showInGameErrorReport` 带防重入；`onError` 改为先落盘再抛。
- 新建 `source/substates/CrashReportSubState.hx`：直接继承 `FlxSubState`（不继承
  `MusicBeatSubstate`，避开 `ClientPrefs.data` / `Pathfinder` 依赖），零资源依赖，
  create/update/close 各自包 try。

### 需要记住的坑

- `FlxState.tryUpdate()` 里 `update(elapsed)` 先跑、`resetSubState()` 后跑。父 state 的
  `update()` 每帧抛异常时，`resetSubState()` 永远执行不到 → 报告界面永远建不出来。
  解法：`openSubState` **之前**先把父 state 的 `persistentUpdate = false`。
- `subState = _requestedSubState` 在 `subState.create()` **之前**赋值，所以用
  `FlxG.state.subState != null` 做防重入是可靠的。
- 项目约定的相机设置：`cameras = [FlxG.cameras.list[FlxG.cameras.list.length - 1]]`。
- `hx::CriticalError` 全 hxcpp 只在 `Debugger.cpp` 的 `HXCPP_DEBUGGER` 分支里调用，
  所以 `onError` 在 Release 下基本不会被触发 —— 降低 Release 原生报告数的是
  `HXCPP_CHECK_POINTER`，不是 `onError`。

### 验证命令（改 source/ 下 .hx 后必跑）


## 第一次实机验证：Haxe 路径接住了，但报告界面建不出来

### 现象

`export/legacy-gc/windows/bin/crash/` 里 18:23:41–18:24:18 出现 14 份
`kind=uncaught_error` / `message=Null Object Reference` 的报告，间隔约 2s
（正好是 `REPORT_DEDUP_WINDOW_MS` 的窗口）。说明 `HXCPP_CHECK_POINTER` 生效了、
Haxe 路径接住了错误，但**错误每帧都在抛**，而且游戏内报告界面没出现，只有原生弹窗。

### 为什么报告界面建不出来

`openSubState()` 只是把请求排进 `_requestedSubState`，真正安装发生在
`FlxState.tryUpdate()` 里的 `resetSubState()` —— 而它排在 `update(elapsed)` **之后**：

```haxe
if (persistentUpdate || subState == null) update(elapsed);   // ← 这里抛异常
if (_requestSubStateReset) { _requestSubStateReset = false; resetSubState(); }  // ← 永远到不了
```

关键：守卫是 `persistentUpdate || subState == null`。`subState` 还是 null 时，
**`persistentUpdate` 无论真假 `update()` 都会跑**，所以"提前把 persistentUpdate 置 false"
根本挡不住安装前的这一帧。必须同步安装。

### 改动

- `CrashHandler.showInGameErrorReport()`：
  - `openSubState(report)` 之后手动补一次 `resetSubState()`，同步装上界面；
  - 再用 `untyped current._requestSubStateReset = false;` 清掉 `openSubState()` 留下的
    重置请求 —— 不清的话下一帧 `tryUpdate` 会再跑一次 `resetSubState()`，此时
    `_requestedSubState` 已是 null，`subState` 会被赋成 null，报告只闪一帧就没了。
    flixel 没有公开的清除方式（`closeSubState()` 只会把它置 true）。
  - 同时压 `persistentUpdate` **和** `persistentDraw`：后者默认是 `true`，
    不压的话父 state 的 `drawUpdate()` 会先跑，抛异常就轮不到子状态画。
  - 去掉 `if (current.subState != null) return false;`：让 `resetSubState()` 自己
    关掉并销毁已有的子状态，报告才能盖在暂停菜单之类的上面。
  - 加了 `in_game_report=` 字段记录上一次展示结果，下次跑就能看到失败原因。
- `CrashSubState` 相应接收并还原 `persistentDraw`；`close()` 里 `super.close()` 也包进 try。

### 原生弹窗的来源（git 历史）

- `d10a5cd7`（2026-08-10，CNE 安卓端）**删掉了 `FlxG.state.openSubState(new ErrorSubState(...))`**，
  换成无条件调用 `SUtil.showPopUp(...)`。
- `SUtil.showPopUp` 在桌面端 → `lime.ui.Window.alert` → `NativeWindow.alert` →
  `NativeCFFI.lime_window_alert` → `SDLWindow::Alert` →
  **`SDL_ShowSimpleMessageBox`**（`lime/git/project/src/backend/sdl/SDLWindow.cpp:490`）。
  这是**阻塞调用线程**的原生模态框。错误每帧都在抛时逐帧调用，就成了"关掉立刻再弹"。
- 现在改成兜底：只有游戏内报告确实展示不了、且本进程还没弹过时才弹一次。
- 注意 `NativeCrashHandler` 的原生弹窗（`novaflare_windows_show_crash_notification`）
  只在 UEF 里调用，一定伴随一份 `native-crash-*-2.txt`，可以用有没有这份文件来区分。

### 顺带确认的事实

- `FlxGame.step()` 里 `if (_nextState != null) switchState();` 排在 `_state.tryUpdate()`
  **之前**（`FlxGame.hx:847`）→ 父 state 每帧抛异常时，`FlxG.switchState()` 仍然有效。
  这是比 subState 更稳的兜底路径（`originfunkin` 分支就是这么走的）。
- `source/substates/ErrorSubState.hx` 是 d10a5cd7 之前用的报错菜单（`MusicBeatSubstate`），
  它的 `create()` 里也写 `FlxG.state.persistentUpdate = false`，关闭时直接
  `switchState` 到 Freeplay/MainMenu 而不是回到崩坏的 state。
- `hx::CriticalError` 只在 `Debugger.cpp` 的 `HXCPP_DEBUGGER` 分支调用，
  14 份报告里没有一份 `kind=hxcpp_critical_error` —— `onError` 在 Release 下确实不触发。

### 待确认

报告文件里的栈仍然是空的（`[haxe_exception_stack]` / `[haxe_call_stack]` /
`[native_hxcpp_exception_stack]` 全空），因为 `HXCPP_STACK_TRACE` 只在 debug 开。
不打开它，Release 下永远只能拿到 `message` 拿不到位置。

## 18:21 那份原生崩溃：定位到 lime.ndll 的 OpenAL 区

`native-crash-20260921-182142-990-p23320-t2332-2.txt` 里 `fault_module=lime.ndll`、
`fault_module_rva=0x30a51d`、`access_address=0x0`。lime.ndll 没有 PDB，
用 `.pdata`（`RUNTIME_FUNCTION` 表，列出镜像里每个函数的起止 RVA，含静态函数）二分定位：

- 崩溃函数：`0x30a260..0x30a7b7`（1367 字节，静态函数），崩在 +0x2bd
- 调用者：`0x3077a0..0x3077cd`（45 字节 thunk），在 +0x13
- 归属：最近的导出是 `alIsEffect @ 0x303ec0`，下一个是 `alGetListener3f @ 0x32ca10`；
  整段 `0x302ef0`–`0x33b270` 全是 `al*` —— **OpenAL Soft**，lime 把它打进了 lime.ndll。

minidump 里的调用链：`rsp` 距栈段顶部只有 0x2a0 字节，`rsp+0x88` 是
`lime.ndll+0x3077b3`（那个 thunk），再往上 `rsp+0xe8` 是 `kernel32!BaseThreadInitThunk`、
`rsp+0x118` 是 `ntdll!RtlUserThreadStart`。
→ **一条工作线程、调用链很浅、刚起步就崩，读地址 0x0。**

结论：这是音频栈自己的崩溃，跟 Haxe 报错路径、原生弹窗都无关；
`HXCPP_CHECK_POINTER` 也覆盖不到（不在 Haxe 生成代码里）。

**铁镐确认：NF 自带的 OpenAL 版本较老，这类崩溃不用管。** 以后遇到
`fault_module=lime.ndll` 且 RVA 落在 `0x2f0000`–`0x33b000` 的，直接归到这一类，
不再往下挖，也不在报错流程里给它兜底。

工具脚本放在 skill 的 `scripts/` 下：
`resolve_rva.py`（RVA → 函数边界 + 库归属）、`walk_minidump.py`（dmp → 调用链，`--above` 只看故障帧）。

- 保留的仍然是两处与"界面是哪个"无关的修复：
  1. **同步安装**（`openSubState()` 后补 `resetSubState()`，再清 `_requestSubStateReset`）——

## 报错界面出现了，但里面没有报错信息 —— 根因是 HXCPP_STACK_TRACE

### 现象

`export/legacy-gc/windows/bin/crash/2026-09-21-23'06'45.txt`：

```
message=Null Object Reference
in_game_report=shown: ErrorSubState     <- 界面确实装上了
[haxe_exception_stack]      <- 空
[haxe_runtime_snapshot]     <- 空
[haxe_exception_stack_raw]  <- 空
[haxe_call_stack]           <- 空
[native_hxcpp_exception_stack]
[]                          <- 空数组，不是 null
```

即：`message` 有值，**所有栈段全空**，所以界面里只有一行 "Null Object Reference"。

### 根因（不是 CrashHandler 的问题，是编译宏）

| 宏 | 少了它会怎样 |
|---|---|
| `HXCPP_STACK_TRACE` | `HX_STACKFRAME` 展开成空（`StackContext.h:81-92`）；`hx::Throw` 里 `__hx_stack_set_last_exception()` 被 `#ifdef` 掉（`src/hx/StdLibs.cpp:61-68`）→ `mExceptionStack` 永远不填 → `__hxcpp_get_exception_stack()` 返回**空数组**（`src/hx/Debug.cpp:544-556`） |
| `HXCPP_STACK_LINE` | 每帧格式化成 `clazz::func::file::0`（`FormatStack`，`src/hx/Debug.cpp:152`），**行号全丢** |

链路：`std/cpp/_std/haxe/NativeStackTrace.hx` 的 `exceptionStack()` →
`__hxcpp_get_exception_stack()`；`haxe.CallStack.exceptionStack(true)`
（`std/haxe/CallStack.hx:63`）→ `NativeStackTrace.toHaxe()` 按 `::` 切成 4 段才产出
`FilePos`。空引用那条路也走 `hx::Throw`（`hx::NullReference` → `__hxcpp_dbg_checkedThrow`
= `hx::Throw`，`src/hx/Debug.cpp:474` + `include/hx/Debug.h:369`），所以宏一开就有栈。

两个宏只在 `HXCPP_DEBUG`/`HXCPP_DEBUGGER` 下自动开（`include/hxcpp.h:109`、
`StackContext.h:18-26`），Release 必须显式写进 `Project.xml`。

### git 时间线（栈是什么时候丢的）

- `9f30a870`（首个提交）：`CHECK_POINTER` + `STACK_LINE` + `STACK_TRACE` 全是**无条件**。
- `ba4ddc4a`（2026-07-27，NovaGC/性能）：五个宏**一起降成 `if="debug"`** ← **报错信息消失的起点**
- `efb67257`（2026-07-31）：`NativeCrashHandler` 上线。
- `d10a5cd7`（2026-08-10）：**删掉 `HXCPP_STACK_LINE`**、`CHECK_POINTER`/`STACK_TRACE` 留 `if="debug"`；
  同时把 `openSubState(ErrorSubState)` 换成 `SUtil.showPopUp` ← **界面消失的起点**

### 本次改动

`Project.xml` 的 `<section if="cpp">`：新增无条件 `<haxedef name="HXCPP_STACK_LINE" />` +
`<haxedef name="HXCPP_STACK_TRACE" />`（`HXCPP_CATCH_SEGV` 按铁镐要求保持 `if="debug" unless="android"`）。

**只改 XML 就够**：生成器无条件 emit `HX_STACKFRAME(&_hx_pos_...)` + `HXLINE(n)`，
是 C++ 侧宏决定它们展开成什么。转发链路 `toolchain/common-defines.xml` 第 12/13/17 行
三个 flag 都在，不需要动 hxcpp。
